Goal

Scale the paper-machine vision system to 16 cameras @ 50 fps global, mixed Mono8 + BGR sensors, with 2000-frame (40 s) events that still get every-frame detail in review — and give the whole fleet one IEEE 1588 (PTP) time base so every event frame across all cameras lands on a single µs-accurate timeline.

Assumes a2A1920-51gm/gcBAS (IMX392, 1920×1200) shortlist cameras. The current scA780-class sensors (782×582) stay valid: if sensor resolution grows, scale the numbers below linearly.

Hardware verdict (all-BGR):

  • RAM: 64 GB is the bare minimum (buffers alone take 43.7 GB) — 128 GB recommended; nothing else may compete for memory at 64 GB.
  • Network: a single 10G NIC is borderline (8.7 Gbps + protocol overhead); bond 2× 10G or move to 25G.
  • Disk: NVMe Gen4 mandatory; ~45 GB/event → plan retention ≈ 20 events/TB.
  • CPU: every scanned frame pays an extra BGR→gray cvtColor pass.
  • Practical advice: prefer Mono8 for the 50 fps lanes; use BGR only where color is genuinely required and run those cameras at lower fps — which requires roadmap item 1 (per-camera FPS-true recording).

2d.GPU — why none today, when to reconsider

The pipeline stores and processes raw uncompressed frames — there is no video codec anywhere, so GPU video acceleration (NVDEC/NVENC/VAAPI) has nothing to decode. All pixel work (meanStdDev, cvtColor, morphology, Qt raster painting) is small, memory-bound, CPU-friendly OpenCV/Qt work; PCIe transfer overhead would eat most GPU gains at small frame sizes.

Reconsider a GPU when any of these enter the roadmap:

  1. AI/ML defect detection (CNN inference, TensorRT/OpenCV-CUDA) — the most likely trigger; rule-based DefectDetector would be replaced/augmented.
  2. 16-stream display bottleneck — 800 fps of convert+scale for live tiles is real CPU load; if profiling shows it hogging cores, move conversion or presentation to GPU (QOpenGLWidget / CUDA convert). Measure first.
  3. Compressed recording — if events were stored as H.264/H.265, NVENC offloads encoding (today's MP4 export is occasional; CPU codec is fine).

Until then: spend the budget on RAM, 10G NICs, PTP switch + grandmaster, and NVMe — those decide whether the 16-camera line flies.

2g.Illumination (strobed LED, matched to 11 m/s web)

Governing constraint — motion blur. Web speed ≈ 665–677 m/min ≈ 11 m/s (docs/machine-reference.md drive anchors). Sharp imaging on a 1920-px sensor needs exposure ≈ 10–25 µs:

FOV widthmm/pixelMax exposure (≤0.5 px blur)
400 mm0.208~9 µs
600 mm0.313~14 µs
1000 mm0.52~24 µs

→ Continuous lighting cannot work at these speeds; strobed LED is mandatory. At 50 fps a 20 µs pulse = 0.1 % duty cycle → LEDs may be overdriven 10–20× rated current within thermal limits. Paper reflectance (~80 %) is favourable.

Sync architecture: camera Flash/ExposureActive output (pylon LineSource / FlashWindow nodes) → LED driver trigger input, per camera. One light per station; no cross-sync needed between stations. Exposure control already exists in CameraDeviceSettingsDialog; flash-output feature is a small later addition. (Strobe timing needs no PTP — it is per-camera hardware I/O; PTP keeps the timestamps aligned.)

2i.Mounting & bracket design

Requirements from our own system: CameraInfo.machinePosition (mm ruler) must stay valid → brackets hold position permanently; paper-machine vibration (11 m/s web) causes blur + FOV drift; wet/hot/dusty zones per §2h; each LED bar must stay co-aligned with its camera.

Two-stage architecture — one base plate per station carries camera AND light:

[walkway / machine structure]

         ├── CAMERA HEAD (yaw/pitch ±5°, focus slide → LOCK)

Adjust once → lock hard (set screws + thread locker). No rubber joints: they creep under vibration. Relative camera↔light alignment survives bumps.

2k.Time sync — which cameras have PTP (verified)

Configuration guidance (Basler-recommended + ours)

  • Enable per camera: GevIEEE1588 / PtpEnable = true (the app already does this on config apply).
  • Basler recommends ANNOUNCE interval 2 s, SYNC interval 0.5 s.
  • Keep the default end-to-end delay mechanism. Peer-to-peer only if every switch in the path is PTP-enabled and configured for P2P.
  • Set a dedicated grandmaster with Priority 1 < 128 (e.g. 100); set ace 2 cameras to 255 so no camera ever arbitrates to master when the GM is present. On scout-class cameras priority is fixed at 128 — the GM still wins on clock class / ID tie-breaks, but you cannot lock cameras out of the arbitration.
  • Do not filter PTP multicast on the switch: E2E uses 224.0.1.129 (announce/sync) and 224.0.0.107 (delay-req).
  • Chunk data must be on with ChunkTimestamp (+ Framecounter) selected, or the app falls back to software arrival stamps (§ Current state).

⚠️ What PTP does and does not give you: with no GPS master the network runs in arbitrary-timescale (ARB) mode — all cameras agree with each other to µs precision, but the epoch is arbitrary and can shift when the grandmaster reboots or a better clock appears. That is enough for cross-camera frame alignment in one event; absolute UTC requires §2m.

2l.Time sync — the switch

The network switch is the middle of the PTP chain. PTP-capable managed switches run as an IEEE 1588 transparent clock (TC) or boundary clock (BC) and compensate for each packet's residence time, so slave offset stays in the µs range across the whole fleet. Plain unmanaged or non-PTP switches still pass PTP, but add asymmetric latency and queueing jitter — offsets degrade toward ms and the app's 1 ms alert will fire on a busy network.

Switch + PTP recipe for this system

  • Topology: 16 cameras → 1G ports (Cat6a ≤ ~90 m or fiber for long runs to the dry end); vision server bonded 2× 10G SFP+ uplinks (LACP); grandmaster on its own port.
  • Jumbo frames (MTU 9000) on camera ports — the a2A1920 at 51 fps is ≈ 940 Mbps and needs MTU 9000 to hit rated fps with headroom.
  • PTP domain 0, E2E delay mechanism, do not IGMP-filter the PTP multicast groups (§2k).
  • QoS: priority-tag PTP event messages if the switch supports it; keep the camera VLAN free of broadcast storms.
  • PoE on the Planet model powers each camera (802.3af, ~7 W) — one drop cable per station for data + power; strobe lights still need their own 24 V feed (§2g).

2m.Time sync — the grandmaster

The grandmaster is the root clock of the PTP domain — every camera slave synchronizes to it (via the switch). Basler's own guidance: "for maximum precision, use PTP-enabled network switches and add an external PTP clock device with a GPS receiver". Three rungs, cheapest to most capable:

RungGrandmasterAccuracy / epochCostWhen to use
0None — best-master arbitration picks a cameracross-cam µs after lock; ARB epoch — shifts on reboot / GM change$0today's default (context: arbitrary-timescale mode). Fine while events only compare cameras to each other.
1Vision server as software master — linuxptp ptp4l in master mode on the 10G NICstable while the server runs; µs-level to cameras; host epoch from its own clock (NTP/GPS)$0budget route; GM disappears on server reboot; no absolute traceability.
2GNSS grandmaster — Meinberg microSync XS / HR (IEEE 1588 PTPv2 + NTP, two PTP ports, GNSS/GPS antenna)UTC/TAI absolute, traceable, GPS holdover; µs end-to-end≈ $3–5k est (quote)⭐ recommended for production: events line up with DCS / OPC UA logs, maintenance records and wall clock.

Why absolute time matters here: sheet-break events already snapshot OPC UA speed tags and trigger times. With a GNSS grandmaster, the frame timestamps in every .bin become UTC — a break can be correlated hour-for-hour with the DCS historian and the drive logs, not just within one event.

Rollout steps

  1. Day 1 (no new hardware): keep PTP enabled (app does this), leave ARB mode, verify all tiles show PTP SLAVE and offsets < 1 ms on the current switch.
  2. Day 2 (switch swap): install a PTP-capable switch (§2l), keep ARB, watch offsets drop to single-digit µs on GevIEEE1588OffsetFromMaster / PtpServoStatus=Locked.
  3. Day 3 (absolute time): add the GNSS grandmaster, Priority 1 = 100 (cameras 255 on ace 2), domain 0, and switch chunk timestamps on. Optionally run ptp4l as a slave on the vision server so host-clock event times match too.

⚠️ Housekeeping: an ARB grandmaster is whoever wins arbitration — if that camera is swapped or power-cycled, the epoch shifts and pre/post-reboot events no longer share a timeline. Log PtpGrandmasterClockID per event so reviewers can detect a timescale jump (the app already reads it into PtpStatus.parentClockId).

4.Software roadmap (ordered)

  1. Per-camera FPS-true recording — the recorder currently sizes all buffers from one global fallback FPS and stores it in every RAW header. It must read each camera's real AcquisitionFrameRate (Pylon node already accessible) so frame counts, event duration, time axis, and slow-motion are honest for mixed-fps / mixed-format lines. Blocks item 2 being trustworthy.
  2. Lazy DETAIL sub-scans (>600-frame events) — keep the whole-event chart at ≤600 samples; on demand, scan ±30 frames around the playhead at stride 1 (≈ 0.4 GB reads) and cache. Delivers every-frame detail at 2000-frame events without the 28.5 GB full scan. This is what makes 2000-frame detail affordable on the hardware above.
  3. Startup FPS-mismatch warning — compare each camera's live ResultingFrameRate vs configured fallback; warn on drift. Cheap guardrail.
  4. PTP chain diagnostics in-app — surface the grandmaster clock ID and per-camera offset (already read) on a time-sync panel; flag ARB-mode (no GPS) and offset creep > 100 µs as advisory — makes §2k–2m observable from LiveDashboard.
  5. 10GigE + kernel tuning — when the 16-camera hardware is built: jumbo frames, ring buffers (net.core.rmem_max), IRQ affinity. See the industrial-vision-networking skill.
  6. Configurable scan cap (optional) — expose kMaxScannedFrames in Config if overview density ever needs tuning.

5.Current state (2026-09-04)

  • main: DETAIL strip (±30 f default, wheel ±10–120, auto-show < 1×), local Y-range label, Recording-settings frame-count info line.
  • PTP runtime exists already: auto-enable on every real camera, 10 s latched status read, Live-View tile badges (SLAVE/MASTER/SYNC/OFF/FAULT), Device-Settings status card with clock IDs, 1 ms offset alert.
  • Recording config: Fallback FPS 10, pre 10 s + post 5 s = 150-frame events.
  • Chunk mode is off in the saved config → events carry software arrival timestamps today (cross-camera comparable, but not sensor-accurate); turning chunk mode on is the step that makes the §2k–2m chain pay off.
  • Parked experiment: experiment/filmstrip-view (unmerged).
